# 0.10.1

## Bug fixes

- **Cluster colors match the colormap.** `so.plot.cluster_image`, `save_cluster_image`, `cluster_legend`, `cluster_selection`, `save_cluster_selection`, `som_clusters` and the colorbars of `cluster_scatter` and `connectivity_graph` now show each cluster in the color with the same index in the colormap. Before, the colormap was scaled to the range of labels present in each image, so images that lacked the highest cluster labels, or that contained unassigned pixels, showed clusters in the colors of other clusters. Colormap names and continuous colormaps, e.g., `colormap="flag"` for segmentation masks with many labels, are still spread from label 0 to the highest label.
- **Unassigned pixels are supported.** Pixels without a nearest SOM node, i.e., all-zero pixels with the cosine metric and constant pixels with the correlation metric, are labelled -1 by `so.dimension.som().label` since 0.10.0. They are now handled throughout:
  - Cluster plots show them transparent (black in `cluster_selection`), and `cluster_location` does not show them as a cluster.
  - `so.spatial.vicinity_composition` counts them neither as a cluster nor as a neighbor, and its permutation test keeps them in place.
  - `so.spatial.autocorrelation` does not analyse them as a cluster, and `so.spatial.local_heteroskedasticity` assigns them to no cluster.
  - `so.spatial.local_autocorrelation`, which operates on the label values, raises a `ValueError` for them.
- **Integer labels of any type are accepted.** `vicinity_composition`, `autocorrelation` and `local_autocorrelation` rejected the `int32` labels returned by `so.dimension.som().label` since 0.10.0. Invalid clustered images now raise a `TypeError` or `ValueError` instead of an `AssertionError`.
